OrangeRails Protocol in Practice: BitBooks V2 Case Study

How a live customer-facing SaaS adopts the OrangeRails Protocol under true zero-knowledge. A worked example of Path B applied to BitBooks V2, the first protocol-driven consumer.

v1.0 · Draft for partner discussion Path B (true zero-knowledge for credentials) YAML load-bearing Internal · shareable with partners

1 Why V2 First

The OrangeRails Protocol promises one thing for every consumer app: publish your App Profile, OR delivers ready-to-insert rows, your insert path stays thin. BitBooks V2 is the first proof. This case study walks the integration end to end so partners and future consumer authors can see the protocol applied to a live, customer-facing accounting product.

⚡

V2 is live

Customers use it now. A working Blink to V2 sync ships real value to real merchants on day one, not a demo with no business owner.

📐

V2 is roughly 80% there

Seven OR-related commits already shipped under the V3 vault pattern. The gap is the protocol contract on the sync call, not the privacy model.

🪶

The rework is small

Most of the work is OR-side (sink adapter, YAML profile, format dispatch). All of that is done. V2-side work is roughly thirteen hours, two days for one engineer.

🔁

V2 becomes the template

Once V2 lands, V3, OW, and Personal each follow the same recipe: one YAML, one sink adapter, browser-side encryption pass for ZK consumers. Build time per consumer drops below a day.

Audience. Partners (Galoy/Blink, Pay with Flash, Lunar Rails, Quiltt) and future consumer authors (every team that wants its app to receive Bitcoin financial data through OR). This case study assumes you have read the protocol design spec first; this is the worked example that makes the spec concrete.
Repos referenced in this case study. OR core lives at MorningRevolution/orangerails. V2 lives at DeeJanuz/bitbooks (private, on Daenon Janis's GitHub profile). V3 lives at MorningRevolution/bitbooks-v3. The full build plan is at orangerails/docs/V2-Integration-Build-Plan.md.

3 Path A vs Path B, The Decision

At V2 setup time, OR offers consumer apps two privacy postures for source-provider credentials. Both are defined in the protocol spec; this section records V2's choice and why.

REJECTED

Path A, Server-Held Key

OR holds the encryption key for source-provider credentials. V2's server initiates a sync without the customer's password being present in the request. Smooth UX: zero password prompts after sign-in.

  • One-click "Sync Now" with no vault unlock
  • No 12-word recovery code needed
  • No browser-derived key plumbing
  • OR breach exposes credentials directly
  • V2 breach + OR breach exposes credentials
  • Trades real privacy for connect-flow ergonomics
CHOSEN

Path B, Browser-Derived Key

The customer's browser derives the key from a vault password. OR receives the key in transit per request, decrypts the source credential in memory, then wipes RAM. V2's server never sees the password or any derived key.

  • Vault password prompt once per browser session
  • 12-word recovery code generated at setup
  • Two-breach floor for credential exposure
  • OR ciphertext alone is useless to an attacker
  • V2 plaintext alone does not leak source credentials
  • Mirror of V3's vault context, applied to V2 verbatim
Why Path B even though V2 stores transactions plaintext. The source-provider credential (Blink API key, Strike OAuth refresh token, Flash long-lived secret) is sensitive in its own right. An attacker who reads it can impersonate the customer at the source provider, drain a Lightning balance, post to a payment processor. That risk exists independently of how V2 stores the transaction history. Path B encrypts the credential at OR with a key the customer's browser holds, so a single breach (V2 or OR) is not enough to lift the credential. Path A would have V2's server hold the key, and any V2 breach would expose the source credential alongside the books.

Threat-model comparison

ThreatPath A REJECTEDPath B CHOSEN
OR data breach (database dump) Source credentials exposed in plaintext or with a key the attacker can also lift. Source credentials are AES-GCM ciphertext. Useless without the customer's vault password.
V2 data breach (database dump) Transaction history exposed. Source credentials may also live here. Transaction history exposed. Source credentials live at OR, not at V2.
Combined V2 + OR breach Source credentials and transaction history both exposed. Source credentials still need the customer's vault password (or recovery code) to decrypt. Two-breach floor holds.
Compelled disclosure to OR operator OR can read source credentials at rest. OR cannot read source credentials at rest. Decryption keys exist for the milliseconds of one HTTP request, then are wiped.
Customer forgets password and loses recovery code No issue; OR can re-issue access via support flow. Bookkeeping for connected accounts is unrecoverable. Customer disconnects and reconnects from sources to start fresh. V2 surfaces a clear warning at setup.
Customer onboarding friction None beyond the sign-in. Vault password prompt at setup, again on first sync per browser session, plus recovery-code reveal. Small but non-zero.
The verdict. The privacy property matters and the UX cost is small enough to absorb. V2 chose Path B. Every BitBooks-family consumer (V3, OW, Personal) inherits the same posture for the same reason.

4 What V2 Mirrors From V3 Verbatim

V3 has been running the Path B vault pattern in production. V2 takes it verbatim, simplified to a single password mode. The list below describes what V2 KEEPS from V3 in the protocol-driven build.

🔐

VaultContext shape

Random 256-bit MEK. Argon2id-derived KEK wraps the MEK. Recovery code wraps the MEK independently. All key material lives in browser memory only, never in cookies, localStorage, or the network.

📜

12-word recovery code

Same fixed 256-word list as V3. Generated once at setup, shown once with a "save this now" reveal screen, encrypted under the MEK and stored at OrangeRailsRecoveryCode.encryptedCodeB64. Customer can re-fetch by entering their password.

🔑

OR subkey derivation

From the MEK, V2 derives orCredsKey via HKDF. orCredsKey is exported as base64 (extractable) and sent to OR per sync request, in transit only. No key material persists on V2's server.

🪟

AddConnectionDialog flow

Five-step UX: provision OR subaccount, vault setup with recovery code reveal, pick provider (Blink), paste API key, browser encrypts and posts ciphertext to OR's or-connection-create. Identical to V3's dialog, simplified copy.

🔁

bb-or-proxy edge function

V2 keeps the same proxy pattern V3 uses: a server-side route adds the platform API key (X-Platform-API-Key header), forwards the body unchanged to OR. Customer never sees the platform key; OR never sees V2's user JWT.

🛟

Recovery and reset routes

app/api/.../orange-rails/recovery-code/ for re-fetch and acknowledge. app/api/.../orange-rails/reset/ for vault password reset (re-wraps MEK with new password). Both KEEP from the existing thin slice.

VaultContext, the mirror in code

V2's VaultContext.tsx is functionally identical to V3's. The shape:

// V2 mirrors V3 verbatim. Random MEK + Argon2id KEK + recovery-code wrap.
// Browser-only. Cleared on tab close.

type VaultState = {
  status: 'locked' | 'unlocked' | 'unprovisioned';
  mek: CryptoKey | null;            // 32 random bytes, AES-GCM
  orCredsKey: CryptoKey | null;     // HKDF-derived subkey, extractable
};

async function unlockVault(password: string, saltB64: string) {
  const salt = decodeB64(saltB64);
  const kek = await argon2idDeriveKey({
    password, salt,
    memoryKiB: 65536, iterations: 3, parallelism: 1,
    hashLen: 32,
  });
  const mek = await unwrapMekWithKek(kek, wrappedMekB64);
  const orCredsKey = await deriveOrCredsKey(mek);
  return { status: 'unlocked', mek, orCredsKey };
}

async function deriveOrCredsKey(mek: CryptoKey) {
  // HKDF-SHA256 with info="or:credentials:v1"
  // extractable=true so we can export to base64 for in-transit handoff to OR
  return crypto.subtle.deriveKey(
    { name: 'HKDF', hash: 'SHA-256', salt: EMPTY, info: infoBytes('or:credentials:v1') },
    mek,
    { name: 'AES-GCM', length: 256 },
    true,                                // extractable for export to base64
    ['encrypt', 'decrypt'],
  );
}
What "browser-only" means here. Password, KEK, MEK, and orCredsKey never leave the browser as plaintext. The exported orCredsKey base64 only travels in TLS-encrypted requests to OR, where it lives in process memory for one request and is then wiped. V2's Postgres holds the salt (vaultSaltB64) and a verifier (vaultVerifierB64, SHA-256 of the MEK), enough to confirm the password is correct without ever holding the password or MEK.

12-word recovery code

The recovery code is the customer's escape hatch when they forget their vault password. V3's pattern, taken verbatim:

  1. At vault setup, generate 12 words from a fixed 256-word list (smaller than BIP39 by design, easier to handwrite).
  2. Encrypt the words under the MEK with AES-256-GCM. Store ciphertext at OrangeRailsRecoveryCode.encryptedCodeB64.
  3. Show the words once on a "save these now" screen, with copy: "If you forget your vault password, this is the only way back into your data. Lose both, lose your bookkeeping for connected accounts."
  4. Customer acknowledges. acknowledged flips true. Words clear from browser memory.
  5. Re-fetch is gated by entering the current password. Reset uses the words to unwrap the MEK, then re-wraps with a new password-derived KEK.

OR subkey derivation

OR uses one subkey from the V2 MEK. The pattern is HKDF with a versioned info string:

SubkeyHKDF infoUsed for
orCredsKey or:credentials:v1 Encrypts source-provider credentials (Blink API key, etc.) at or-connection-create time. Sent in transit per or-sync call so OR can decrypt the credential, fetch from the source, then wipe.

Future subkeys (transaction-list re-key, per-source isolation) sit on the same HKDF pattern with new info strings, so adding them is a one-line change in VaultContext.

5 What V2 Changes, The Protocol Contract

This is the only protocol-level change on the V2 side. Everything in section 4 stays. The sync call shape changes from "encrypted-payload store, two-roundtrip pull, browser decryption" to "format dispatch, one roundtrip, ready-to-insert rows."

BEFORE

Encrypted-payload store flow

V2 sent both credentials_key and transactions_key to or-sync. OR fetched from Blink, encrypted each transaction's payload under transactions_key, persisted ciphertext. V2 then called or-transactions-list, decrypted each row in the browser, mapped to V2 schema, inserted.

  • Two OR roundtrips per sync (sync, then list)
  • OR persists encrypted transaction blobs
  • Browser does a decryption pass
  • V2 owns the canonical-to-V2 mapping locally
  • V3-style flow, but V2 stores plaintext anyway, so the encryption pass is wasted work
AFTER

Format dispatch flow

V2 sends only credentials_key and format: 'bitbooks-v2'. OR loads the V2 App Profile YAML, decrypts the source credential in memory, calls Blink, runs the V2 sink adapter via the engine, returns V2-shaped Prisma rows in the response. V2 inserts directly.

  • One OR roundtrip per sync
  • OR persists no transaction data
  • No browser decryption pass
  • OR owns the canonical-to-V2 mapping (in YAML + sink TS)
  • Matches V2's plaintext storage choice without compromising credential ZK

The new request

// V2 to OR. credentials_key still travels in transit; transactions_key gone.
POST /functions/v1/or-sync
X-Platform-API-Key: <V2 platform key>
Content-Type: application/json

{
  "subaccount_id": "<V2 org's OR subaccount UUID>",
  "credentials_key": "<base64 raw 32 bytes, the orCredsKey from VaultContext>",
  "format": "bitbooks-v2"
}

The new response

{
  "synced": 5,
  "connections": [
    { "connection_id": "...", "synced": 5, "next_cursor": "..." }
  ],
  "rows": {
    "Wallet":           [{ "sourceWalletId": "...", "__resolveCoa": { /* hint */ }, ... }],
    "Transaction":      [{ "id": "...", "__resolveWalletId": { ... }, "amount": "0.00045000", ... }],
    "JournalEntry":     [{ "id": "...", "refNum": "JE-OR-...", ... }],
    "JournalEntryLine": [{ "journalEntryId": "...", "__resolveCoa": { ... }, "debit": "0.00045000", ... }]

}
Backward compatible. When format is absent on the request, OR runs the existing encrypted-payload path unchanged. V3 keeps using that path until it migrates to format=bitbooks-v3. Two consumer postures (V2 + V3) coexist on the same or-sync endpoint without flagging or branching at the call site.
What still travels in transit. credentials_key (the orCredsKey base64) still flows in transit per request. OR needs it to decrypt the source-provider credential at fetch time. The key exists in OR memory for the duration of the request, then is wiped. No persistence, no logging, verifiable in the open-source code. Path B's privacy contract is unchanged by the format-dispatch flow; only the response shape changes.

6 The YAML Is Load-Bearing

The V2 App Profile YAML lives at supabase/functions/_shared/sinks/profiles/bitbooks-v2.yaml in the OR repo. The runtime parses it on edge-function startup, validates structure, caches per format slug, and uses it on every sync to drive two decisions per transaction.

📒

account_mapping_rules

First-match-wins. Each rule has either a when clause (matched against the canonical transaction's type + direction) or default: true. The first match returns its debit and credit CoA hints. The engine resolves from: canonical.X, from: derived.X, and from: input.X references at runtime.

🚦

status_to_v2

Provider status string to V2's TransactionStatus enum, with the default key as the fallback. Edit the mapping, redeploy, the next sync uses the new mapping. No TypeScript change.

How the engine resolves from: references

At sync time, OR builds a per-transaction context with three namespaces:

  • canonical.*: the canonical transaction itself (id, type, direction, timestamp, amount, asset, source_wallet_id, description, fiat_equivalent.rate, ...).
  • derived.*: shapes the sink computes once per transaction (asset, amount as Decimal-shaped string, now, parent_je_id, line.account_role, line.debit, line.credit, wallet_default_name, wallet_type).
  • input.*: passed in from the sync request (org_id, or_connection_id).

The engine walks the rule list, finds the first match against the canonical context, returns the rule's debit and credit objects with all from: references resolved to literal values. The resolved objects feed directly into the __resolveCoa hints embedded in JournalEntryLine rows.

What "load-bearing" buys you. Daenon wants to remap "lightning in" from SALES to OTHER_INCOME for one of his customers? Edit four lines in the YAML, redeploy the edge function, the next sync uses the new mapping. Zero TypeScript change. Zero V2-side change. Zero customer downtime. The protocol's value compounds when the rules live in YAML and the engine reads them.
What stays in TypeScript for now. The Wallet, Transaction, JournalEntry, and JournalEntryLine row shapes still live in _shared/sinks/bitbooks-v2.ts. Lifting row construction itself to YAML is a candidate when the protocol picks up its third consumer (OW or Personal); two-consumer YAML lifting is premature.

7 The V2 Sink Adapter

The sink adapter at supabase/functions/_shared/sinks/bitbooks-v2.ts is the TypeScript half of V2's App Profile. It receives a normalized canonical transaction and the engine's resolved rule context, builds Wallet / Transaction / JournalEntry / JournalEntryLine objects shaped exactly as V2's Prisma models expect, and embeds __resolve* hints for the bits that V2 must resolve at insert time against its local Prisma client.

The SinkAdapter interface

// supabase/functions/_shared/sinks/types.ts

export interface SinkAdapter<TOut> {
  slug: string;
  canonicalVersion: 'v0' | 'v1';
  acceptsModules: CanonicalModule[];
  build(tx: NormalizedTransaction, ctx: SinkContext): TOut | null;
  flush?(ctx: SinkContext): TOut[];
}

export interface SinkContext {
  orgId: string;
  orConnectionId: string;
  profile: AppProfile;          // loaded from YAML, validated
  engine: RuleEngine;            // findMatchingRule + mapStatus
  now: Date;
}

export type SinkOutput = {
  Wallet?: unknown[];
  Transaction: unknown[];
  JournalEntry: unknown[];
  JournalEntryLine: unknown[];
};

The __resolve* hint pattern

OR cannot reach into V2's Postgres to do a find-or-create on ChartOfAccount or Wallet. Instead, OR emits resolve hints embedded in the row, and V2's sync handler resolves them at insert time using V2's Prisma client.

Hint keyWhat V2 does
__resolveWalletId Find a Wallet by sourceWalletId (UNIQUE). Replace with the resolved primary key.
__resolveCoa Find-or-create a ChartOfAccount by (accountType, accountSubType, name?, isWallet?, currency?). Auto-create a "Suspense" CoA on first encounter for fallback rows.
__resolveContactId Find-or-create a Contact by (name, kind). Used when canonical transactions carry a counterparty.
__resolveSystemUser Find-or-create the OrangeRails system user (the one assigned as createdById / postedById on JEs).

Sink output, sketch

export const bitbooksV2Sink: SinkAdapter<SinkOutput> = {
  slug: 'bitbooks-v2',
  canonicalVersion: 'v0',
  acceptsModules: ['bitcoin'],

  build(tx, ctx) {
    const derived = buildDerivedContext(tx, ctx);
    const rule = ctx.engine.findMatchingRule(ctx.profile, tx, derived);
    if (!rule) return null;

    const jeId = crypto.randomUUID();
    const v2Status = ctx.engine.mapStatus(ctx.profile, tx.status);

    return {
      Wallet: derived.isFirstAppearance ? [buildWalletRow(tx, derived, ctx)] : [],
      JournalEntry: [buildJeRow(jeId, tx, derived, ctx)],
      JournalEntryLine: [
        buildLineRow(jeId, 'debit', rule.debit, tx, derived),
        buildLineRow(jeId, 'credit', rule.credit, tx, derived),
      ],
      Transaction: [buildTransactionRow(jeId, v2Status, tx, derived, ctx)],
    };
  },
};

V2's sync-handler.ts sees __resolveCoa, runs its find-or-create against ChartOfAccount with the embedded criteria, replaces the hint with the resolved chartOfAccountId primary key, then runs prisma.journalEntryLine.create({ data }) inside a transaction.

V2's sync-handler.ts, the new file

import { prisma } from '@/lib/prisma';

export async function applyOrSyncResponse(
  orgId: string,
  orConnectionId: string,
  response: OrSyncFormattedResponse,
) {
  // V2 stores plaintext at rest. requires_encryption should be empty.
  if (response.metadata.requires_encryption.length > 0) {
    throw new Error(
      `Unexpected encryption fields for V2 sink: ${...}`,
    );
  }

  const resolvers = makeResolvers(orgId, orConnectionId);

  await prisma.$transaction(async (tx) => {
    // Order matters. Wallet must exist before Transaction references it.
    for (const w of response.rows.Wallet ?? []) {
      await resolvers.resolveAndUpsertWallet(tx, w);
    }
    for (const je of response.rows.JournalEntry) {
      await resolvers.resolveAndCreateJE(tx, je);
    }
    for (const line of response.rows.JournalEntryLine) {
      await resolvers.resolveAndCreateLine(tx, line);
    }
    for (const t of response.rows.Transaction) {
      await resolvers.resolveAndCreateTransaction(tx, t);
    }
  });

  return { synced: response.rows.Transaction.length };
}

The route at app/api/.../wallets/[walletId]/sync/route.ts wires it together:

import { syncOrgFromOr } from '@/lib/orange-rails/client';
import { applyOrSyncResponse } from '@/lib/orange-rails/sync-handler';

export async function POST(req: Request, { params }) {
  const { organizationId, walletId } = params;
  await assertMember(req, organizationId);

  // Browser-derived credentials key arrives in the request body
  const { credentials_key } = await req.json();
  if (!credentials_key) return badRequest('credentials_key required');

  const conn = await prisma.orangeRailsConnection.findUnique({
    where: { organizationId },
  });
  if (!conn) return notFound();

  const result = await syncOrgFromOr({
    subaccountId: conn.orPlatformUserId,
    credentialsKeyB64: credentials_key,
  });

  const stats = await applyOrSyncResponse(organizationId, conn.id, result);

  return Response.json({ ok: true, ...stats });
}

8 End-to-End Sequence

The full flow from "customer clicks Sync" to "books update," with what happens at each layer.

The seven user-visible steps

1

Customer signs into V2

Standard Better Auth flow at app.bitbooks.com. Organization context loads. The customer has not yet provisioned an OR vault.

2

Admin to Connectors to "+ Add Connection"

V2 calls the setup route. First-time customer: a vault is provisioned (random MEK in the browser, password-derived KEK wraps it, 12-word recovery code generated and shown once). Customer saves the recovery code. OR subaccount provisioned via or-platform-user-create.

3

Picks "Blink", pastes the API key

Browser derives orCredsKey from the MEK. Browser AES-GCM encrypts the API key locally. Posts ciphertext to OR's or-connection-create. The plaintext key never leaves the browser.

4

Returns to Connectors list

OR confirms storage. V2 displays the connection row (status, last_sync_at). Wallet rows exist on V2 only after the first successful sync; not pre-created.

5

Clicks "Sync now"

Vault unlock prompt if locked; otherwise the in-memory keys are already there. Browser exports orCredsKey as base64. V2 server route forwards it (in transit only, no persistence) to OR's or-sync with format=bitbooks-v2.

6

OR delivers V2-shaped rows

OR loads the YAML profile, decrypts the credential in memory, calls Blink, runs the V2 sink adapter, returns rows. V2's applyOrSyncResponse resolves __resolve* hints, runs Prisma upserts in a transaction.

7

Customer sees the transactions

Transactions list refreshes. Wallet appears with current balance. JE pairs balance to zero. Customer's books are up to date with five Lightning receipts and one on-chain payout.

9 Multi-Connection Bulk Sync

A typical V2 customer is a small accounting practice or a Bitcoin-native business. They might run twenty connections: Blink for their working balance, Strike for incoming wires, Flash for the merchant invoice product, plus one or two on-chain wallets per legal entity. Today (under the encrypted-payload-store flow) every connection's sync requires a fresh password entry.

The friction problem. Twenty password prompts to update twenty connections is unacceptable. Customers will avoid syncing, books will go stale, the value of the connector evaporates.

The fix, one prompt per browser session

Once the customer unlocks the vault, the MEK and orCredsKey live in browser memory until refresh or close. The "Sync All" button runs the per-connection sync sequentially using the in-memory keys, never re-prompting. Tab close = vault locks = keys gone, customer must re-enter on next sync.

// components/admin/admin-connectors.tsx, "Sync All" handler
async function syncAll() {
  if (vault.status !== 'unlocked') {
    await unlockPrompt();                  // shows password modal once
  }
  const credsKeyB64 = await vault.exportOrCredsKeyB64();

  const results = [];
  for (const conn of connections) {
    try {
      const r = await syncOneConnection(conn.id, credsKeyB64);
      results.push({ ok: true, ...r });
    } catch (err) {
      results.push({ ok: false, error: String(err) });
    }
  }
  surface(results);                          // per-connection success/failure badges
}
V3 will pick up the same pattern. V3's vault context already supports multi-connection in memory; what V3 lacks today is the format-dispatch sync flow. After V2 lands, V3 migrates to format=bitbooks-v3 and gets bulk sync as a side effect.

12 Lessons From The Rework

Three lessons earned the hard way during the V2 rework. Each one shaped the protocol's current shape.

🔪

Build the whole flow on day one

The first V2 attempt sliced the work into thin layers (schema, then routes, then UI, then sync). Each slice was small and individually correct, but the slices had chicken-and-egg dependencies that fragmented the integration. The next consumer build will land the whole flow at once even if one or two layers are stub-quality on day one.

🎯

Don't trade privacy for storage convenience

An earlier draft of this plan asked: "V2 stores transactions plaintext anyway, why bother encrypting credentials?" The answer is that the source credential is a separate sensitive thing, in addition to the transaction history. Path B protects the credential whether or not the books are encrypted. Don't trade the credential's privacy property for an easier UX.

📜

YAML-as-runtime compounds

The protocol's value compounds when the rules live in YAML and the engine reads them. Each consumer authors one YAML profile and one sink adapter; rule edits ship without TypeScript changes. The first consumer is the moment you find out which decisions belong in YAML and which stay in code; V2 is where that line got drawn.

The third lesson, expanded. When you author a YAML profile in YAML alone, you can give the YAML to your accounting team or a domain expert, they can draft new rules without writing code, and the protocol's runtime will obey on the next deploy. That feedback loop is the protocol's accelerant. The longer you keep rules in code, the slower every consumer's onboarding gets.

13 What This Unlocks For V3, OW, Personal

V2 is the proof of pattern. Each of the three remaining BitBooks-family consumers follows the same recipe with one delta.

ConsumerYAML profile slugSink adapterEncryption pass at insertEstimate
BitBooks V2 bitbooks-v2 _shared/sinks/bitbooks-v2.ts None (plaintext at rest) Two days, this case study
BitBooks V3 bitbooks-v3 _shared/sinks/bitbooks-v3.ts Browser-side AES-GCM with the org-scope DEK before insert Three days, larger because V3 retires orImportBridge.ts and the local canonical-to-V3 mapping it owns today
OrangeWay (OW) orangeway _shared/sinks/orangeway.ts Browser-side AES-GCM (OW is fully ZK like V3) One day, fresh consumer with no migration debt
BitBooks Personal bitbooks-personal _shared/sinks/bitbooks-personal.ts Browser-side AES-GCM (mirrors V3) One day, fresh consumer, simpler schema than V3
The compounding payoff. The first consumer (V2) costs a couple of days. The second consumer (V3) takes three days because of the migration cost from its existing local mapper, not the protocol cost. From the third consumer onward, build time is measured in hours, not days, because the protocol's hard parts (canonical model, engine, profile loader, format dispatch on or-sync) are reused and only the consumer-specific YAML + sink TS is new work.

What partners get

  • Galoy / Blink: the live source adapter today, plus the BitBooks family as four downstream consumers without writing any V2/V3/OW/Personal mapping code. Blink ships once into OR, every consumer receives Blink data.
  • Pay with Flash: when Flash ships its source adapter, every BitBooks consumer picks Flash up automatically. Same pattern for Strike, Lunar Rails, BTCPay.
  • Future consumers (rotki, Maybe Finance, Firefly III, partner accounting products): author one YAML, one sink TS, one platform key registration. Days to integrate, not weeks. Day-one access to every source already in OR's catalog.
