⚡ ORANGERAILS PROTOCOL

Build once. Connect everywhere.

A universal Bitcoin financial data layer — open spec, zero-knowledge, source/sink architecture. Every Bitcoin service connects once. Every accounting and finance app receives data already shaped for its tables. The protocol that turns N × M integration work into N + M.

v1.0 · Draft for partner discussion Apache 2.0 · CC-BY-SA spec Bitcoin-first Zero-knowledge by default Designed alongside Lunar Rails + Flash

1 Why This Exists

Every accounting product that wants to handle Bitcoin data faces the same wall: each Bitcoin service (wallet, exchange, payment processor, custody, mining pool) speaks its own dialect. Each accounting product writes its own translator for each service. The work doubles every time either side adds a member.

The OrangeRails Protocol fixes this by sitting between sources and apps as a universal translator. One canonical format. Source adapters translate provider APIs into it. Sink adapters translate it into the shape each app needs. End users connect once and get everything — no per-app integration code, no per-source parser duplication.

Zero-knowledge by default. Provider credentials are encrypted in the user's browser before they reach the OrangeRails server. The server stores ciphertext only. Decryption keys exist on the server only for the milliseconds of an active sync request. No background polling means no need to hold keys at rest. This isn't a feature — it's the architecture.
The realization that prompted this protocol: we were building Strike support inside BitBooks V3. Then noticed: V2 will need the same Strike code. So will OrangeWay. So will every future BitBooks family product. And every new source — Cash App, BTCPay, Lunar Rails, Flash — multiplies the work. The fix isn't more parsers. It's a layer that owns the translation in one place, and a contract that lets both sides evolve independently.

2 The N × M Problem

Without a canonical format, every consumer app needs custom code for every data source. Five sources × four apps = twenty integrations to write, test, and maintain. Add a sixth source = four more parsers. Add a fifth app = five more parsers. The cost grows multiplicatively.

The current shape: every app re-implements every source.

Every red dashed line is parsing code, account-mapping logic, and edge-case handling that exists in N places. When Strike adds a new field, every app updates. When V3 changes its schema, every source's V3 mapping changes. The system is fragile in proportion to N × M.

3 The Pivot — Three Layers

Insert a canonical format in the middle. Source adapters translate IN. Sink adapters translate OUT. Now adding a source costs one translator (every app gets it free). Adding an app costs one translator (every source flows in free).

The Protocol shape: every translator is owned in one place, lives once, benefits everyone.
The math. 10 sources × 10 apps = 100 integrations the old way. 10 + 10 = 20 the protocol way. Every new source onward is one translator and is instantly available to every app. Every new app onward is one translator and instantly accepts every source.

5 The Canonical Model

Five entities. The shared format every source translates INTO and every consumer translates FROM. Versioned (v1, v2, v3 over time) so the protocol can evolve without breaking everyone at once.

EntityPurposeExamples
Transaction One movement of value Lightning payment, on-chain tx, OTC trade, fiat settlement, refund, fee, spot trade, staking reward
Account A wallet, exchange account, custody position, bank account Blink BTC wallet, Kraken Spot, Lunar Rails OTC desk, Flash Lightning address, Quiltt Connection
Balance Snapshot of holdings at a moment "Account X holds 0.5 BTC + $1,200 as of 2026-04-28 14:30"
Invoice Demand for payment Lightning invoice, BOLT12 offer, Flash hosted invoice, BTCPay invoice, Stripe-style invoice
Customer Counterparty (when known) "Acme Trading Desk" on a Lunar Rails OTC ticket, "Bob Smith" on a Flash recurring subscription

Each entity has a stable schema, a version field, and an optional raw escape hatch for provider-specific fields that aren't part of the contract but might be useful to a sink that wants them.

6 Canonical Transaction (v1)

Synthesized from Blink, Lunar Rails, Flash, Strike, BTCPay, and CCXT exchange schemas. Designed to round-trip every Bitcoin financial event seen in production today.

interface CanonicalTransaction {
  // Identity
  id: string;                     // OR-generated, stable across syncs
  source_id: string;              // The provider's own ID (for dedup)
  canonical_version: 'v1';
  provider: 'blink' | 'lunar-rails' | 'flash' | 'strike'
          | 'btcpay' | 'csv' | 'ccxt:kraken' | 'ccxt:coinbase'
          | 'simplefin' | 'quiltt' | 'plaid' | 'bitbooks-v2' | 'bitbooks-v3' | string;
  account_id: string;             // canonical Account.id this belongs to

  // What kind
  type:
    | 'lightning_payment'          // Lightning sent/received
    | 'onchain_transfer'           // BTC on-chain
    | 'otc_trade'                  // BTC ↔ fiat OTC
    | 'spot_trade'                 // exchange spot trade (CCXT)
    | 'margin_trade'               // leveraged spot
    | 'derivative_trade'           // futures / options / perps
    | 'fiat_settlement'            // wire / SEPA / SWIFT / stablecoin
    | 'invoice_payment'            // payment of an invoice (commerce)
    | 'subscription_charge'        // recurring billing (Flash, Stripe-style)
    | 'staking_reward'             // PoS yield, exchange staking
    | 'lending_interest'           // exchange-managed lending interest
    | 'mining_payout'              // mining pool payout
    | 'airdrop'                    // free token receipt
    | 'referral_reward'            // promo / affiliate
    | 'refund'                     // refund of a previous tx
    | 'fee'                        // standalone fee (network, routing, spread)
    | 'internal_transfer'          // movement between own accounts
    | 'gift'                       // incoming or outgoing gift
    | 'fork_receipt'               // chain-split coins received
    | 'unknown';                   // adapter couldn't classify
  direction: 'inbound' | 'outbound' | 'internal';
  status: 'settled' | 'pending' | 'failed' | 'expired' | 'refunded';

  // When
  occurred_at: string;            // ISO 8601 — when the value moved
  settled_at?: string;            // when it became final (OTC, on-chain confirmation)

  // How much
  amount: {
    value: string;               // string for precision (BigDecimal)
    unit: 'sat' | 'btc' | 'usd' | 'eur' | 'cad'
        | 'usdt' | 'usdc' | string;     // ISO 4217 or BTC unit
  };
  fiat_equivalent?: {              // optional FMV at occurred_at
    value: string;
    currency: string;             // ISO 4217
    rate: string;                 // unit rate used
    rate_source: string;          // 'lunar-rails' | 'flash' | 'coingecko' | provider
    rate_timestamp: string;
  };
  fees: Array<{
    type: 'network' | 'routing' | 'spread' | 'commission' | 'platform';
    amount: { value: string; unit: string };
    payer: 'sender' | 'receiver';
  }>;

  // Trade extension (when type is *_trade)
  trade?: {
    venue: string;                // 'kraken' | 'coinbase' | 'binance'
    pair: string;                 // 'BTC/USD' | 'ETH/BTC'
    side: 'buy' | 'sell';
    base: { value: string; unit: string };    // e.g. 0.5 BTC
    quote: { value: string; unit: string };   // e.g. 21000 USD
    price: string;                // 42000 (1 BTC = 42000 USD)
    order_id: string;
    order_type: 'market' | 'limit' | 'stop' | 'stop_limit' | 'oco';
    fill_type: 'maker' | 'taker';
    leverage?: string;            // margin_trade / derivative_trade
    sub_account?: string;
  };

  // Cost basis (for tax accounting)
  cost_basis?: {
    method: 'fifo' | 'lifo' | 'hifo' | 'specific_id' | 'acb';
    lots_consumed?: Array<{
      acquired_at: string;
      quantity: string;
      basis_per_unit: { value: string; currency: string };
    }>;
    realized_gain?: { value: string; currency: string };
  };

  // Context
  counterparty?: {
    name?: string;
    identifier?: string;          // address, node pubkey, bank account, NWC URI
    type?: 'wallet' | 'exchange' | 'bank' | 'lightning_node'
         | 'business' | 'individual';
  };
  memo?: string;
  reference?: string;              // OTC ticket, invoice number, order ID
  related_transaction_ids?: string[];   // linked OTC + settlement, refund→original

  // Provider-specific extras (escape hatch — not part of contract)
  raw?: Record<string, unknown>;
}
Key design choices. Strings for amounts (no floating-point loss for sats and fiat cents). Versioned per record (lets v2 ship without breaking v1 consumers). Closed enum for type with unknown escape. raw field for adapter-specific extras. Deliberate FDX-style separation between amount (the value moved) and fiat_equivalent (the FMV).
Bitcoin-first, multi-asset honest. OrangeRails is Bitcoin-first by motivation, by Lightning-native architecture, and by primary focus. But the protocol can't pretend a user's Kraken account doesn't hold ETH or that an FBAR-relevant USDT balance doesn't exist — pretending would lose real data the user needs in their books. So amount.unit is an open string (sat, btc, usd, eur, usdt, usdc, or anything a source actually emits), and types like airdrop, fork_receipt, spot_trade, staking_reward cover events that aren't strictly Bitcoin. When OR wraps CCXT (100+ exchanges) or Quiltt (banks + brokerages), non-Bitcoin assets flow through naturally because that's what users hold. The Bitcoin-first stance is about what we optimize for — Lightning lifecycle, on-chain confirmations, Bitcoin-specific FMV — not about artificially restricting the canonical model. Sink consumers that only care about Bitcoin (e.g., a strict-BTC accounting product) filter on amount.unit ∈ {sat, btc} in their App Profile.

7 Source Adapters

Each source adapter is a self-contained module that knows how to talk to one provider and emit canonical entities. Lives in OR's adapter codebase. Independently deployable, testable, license-tagged.

interface SourceAdapter {
  provider: string;
  authType: 'api-key' | 'oauth' | 'webhook' | 'csv-upload' | 'mtls';

  // Exchange creds for accounts visible to this connection
  fetchAccounts(creds: DecryptedCreds): Promise<CanonicalAccount[]>;

  // Pull transactions since cursor
  fetchTransactions(creds: DecryptedCreds, params: {
    accountId: string;
    since?: string;
    cursor?: string;
  }): Promise<{ transactions: CanonicalTransaction[]; nextCursor?: string }>;

  // Optional — for sources that webhook-push (Flash, BTCPay)
  handleWebhook?(payload: unknown, signature: string): Promise<CanonicalTransaction[]>;

  // Optional — fetch current balance
  fetchBalance?(creds: DecryptedCreds, accountId: string): Promise<CanonicalBalance>;

  // Optional — invoice-issuing sources (Flash, BTCPay, Stripe-style)
  fetchInvoices?(creds: DecryptedCreds, params): Promise<CanonicalInvoice[]>;
}

8 Sink Adapters — The New Concept

This is the missing layer. A sink adapter lives in OR, owned by the consumer app. It says: "given a canonical transaction, produce rows ready to insert into MY tables, in MY shape, with MY accounting rules applied."

interface SinkAdapter {
  app: string;                            // 'bitbooks-v2', 'bitbooks-v3', 'orangeway'
  version: string;                        // '2026.4.1'
  canonical_version_supported: 'v1';

  toAppShape(input: {
    transaction: CanonicalTransaction;
    account_mapping: AccountMapping;       // app's chart of accounts
    org_id: string;                        // app's org/tenant identifier
  }): AppShapeOutput;

  // For double-entry apps (V2, V3)
  toJournalEntries?(input: {
    transaction: CanonicalTransaction;
    account_mapping: AccountMapping;
  }): JournalEntryDraft[];

  output_schema: JsonSchema;                // OR validates output against this
}

interface AppShapeOutput {
  rows: Record<string, unknown[]>;        // { transactions: [...], journal_entries: [...] }
  metadata: {
    canonical_id: string;
    requires_encryption?: string[];        // fields the app's browser must encrypt (V3)
  };
}

Delivery is pull-through. OR is a translator, not a storage service.

The cleanest delivery model — and the one OR uses by default — is pure pull-through. The consumer app initiates every sync when its user is online. OR fetches from the provider, translates to the consumer's shape, returns the rows in the response, and wipes the request from memory. OR holds nothing between sessions except encrypted credentials (necessary to function) and routing metadata (subaccount IDs, last-sync cursors). User data is never at rest on OR's server.

ModeWhenFlow
Pull-through (default for everyone) Always. Every consumer, every provider that supports fetch-since-cursor. User opens app → vault unlocks → app calls or-transactions-list?format=<app>&since=... with the user's session key in-transit → OR decrypts the stored credentials in memory → OR calls the provider's fetch-since-cursor → OR translates to canonical → OR runs the consumer's sink adapter → returns ready-to-insert rows in the response → OR's RAM cleared. Done.
Webhook wake-up (optional accelerator) Provider supports webhooks AND consumer wants faster freshness. Provider fires webhook → OR receives event metadata (no canonical payload stored) → OR sends a Web Push / service-worker ping to the consumer app: "new data available, sync now." → Consumer app wakes → normal pull-through flow runs. OR stores no data; the webhook is just a doorbell.
Direct push (non-ZKA consumers only) V2-style consumer that stores plaintext. Enterprise tier. OR POSTs app-shaped rows directly to the consumer's webhook in real time. Allowed because the consumer doesn't need a per-user encryption key on receipt.
Opt-in real-time alerting (rare, disclosed) User explicitly wants notifications even with app closed. User enrolls in alerting mode → OR holds a server-side alert key per Architecture v1.0 §11.1 → OR can evaluate threshold rules ("notify on >1 BTC inbound") on canonical events without storing the payload. Reduced privacy, explicitly disclosed at enrollment, never the default.
Why we are not a storage business. Holding user payloads — even encrypted, even with public-key envelopes that only the user can open — would make OR a data custodian: retention policies, deletion-on-request handling, breach-disclosure obligations, regulatory scrutiny in every jurisdiction. We avoid all of that by being a translator, not a storage service. The trade-off: webhook-only providers (rare) can't fully real-time-deliver if the user is offline. Acceptable cost for a much simpler privacy story and a much smaller attack surface.
What providers support pull-through today. Blink ✓, Strike ✓, Flash (per integration brief) ✓, BTCPay ✓, Lunar Rails (per PRD) ✓, every CCXT-wrapped exchange ✓, Quiltt's GraphQL ✓. Effectively every well-designed provider supports fetch-since-cursor. The webhook wake-up mode is a freshness accelerator, never a data delivery requirement.

9 The App Profile Registry

When a consumer app registers as an OR platform, it ALSO publishes its App Profile. Stored in OR's app_profiles table, owned by the platform, editable from the Developers tab on orangerails.com/app.

What's plaintext TODAY — and why (each one earns its place)

Plaintext fieldArchitectural reason
id (every table) Row primary key. Random UUID. No business information content. Required for joins, RLS, and indexing.
org_id (every tenant table) Foreign key to organization. Random UUID. Used by Postgres Row-Level Security to enforce tenant isolation server-side. Encrypting it would break RLS.
occurred_at, created_at, last_sync_at, all dates Server-side date filtering (decision D-009 in BB-VAULT-ARCHITECTURE). Without plaintext dates, every report would download the full table. Trade-off documented: server can see "this org had N transactions in March" but cannot see amounts, accounts, or business context.
key_version Crypto versioning metadata. Tells the decryptor which key generation produced this row. Not data. Required for safe key rotation.
wallet_id, contact_id, cala_tx_id, cala_account_id, journal_entry_id, parent_cala_account_id Foreign-key UUID references. All random UUIDs — leak no patterns. The names sitting at the end of these references are encrypted in their own tables. Required for relational integrity.
provider (in connections) — e.g. "blink" Tells OR which source adapter to invoke for sync. Operationally required. Reveals "this user has a Blink connection" to anyone with DB access — but not amounts, accounts, or transaction content. Documented trade-off (Architecture v1.0 §11.2 "metadata is partially visible").
subaccount_id (in OR connections) Opaque UUID linking the user to OR's subaccount. Random. Cannot be reversed to identity.
Cala's account_id (UUID), debit/credit direction, dates Cala stores random UUIDs (no pattern), structural debit/credit (required for double-entry validity), plaintext dates (filtering). Cala's units (amount) and currency are sent as encrypted ciphertext strings, not plaintext. See "Cala's status today" below.
Dual-currency metadata flags: primary_currency_at_posting, rate_pending, rate_asof, pinned_rate_id, dual_amounts_backfilled, manual_rate_reason, manual_rate_source Process state for the rate-pinning workflow, not financial values. The actual rate values themselves are encrypted (encrypted_posted_rate). These flags drive backfill UI and validation but reveal no business data.
account_name + account_code on cala_account_map Overwritten with crypto.randomUUID() on encrypt. They look plaintext in the column, but the value is a random UUID, not the real name. The real name lives in encrypted_name. This is the placeholder pattern that lets Cala have a non-null name field without ever seeing the real one.
Auth-layer user.email (Supabase Auth) Required for login. Stored by Supabase Auth, not the vault. Outside the vault MEK key hierarchy by design.

Cala's status today vs Track A formal blind_mode

📍 Today (production)

V3 sends encrypted ciphertext strings through Cala's existing units and currency string fields. Cala happily stores them as opaque text. Cala's account IDs are random UUIDs. The data has zero business value to a Cala-DB reader because everything sensitive is base64 ciphertext.

Functional zero-knowledge — but the "ciphertext in a string field" pattern is a clever-use of an existing field, not a declared first-class Cala feature.

🔜 Track A — Cala blind_mode fork (in progress)

Formal Cala fork that adds blind_mode to journals as a declared feature. Encrypted-amount fields become first-class types. Same security guarantee as today, but Cala upstream has explicit support instead of an implicit pattern.

The fork closes the "looks weird upstream" gap and unlocks future Cala-side optimizations (e.g. homomorphic operations on ciphertext sums, decision D-002).

Trade-off: complexity + filtering performance hit. Not yet on the roadmap; listed here so the protocol doc is honest about what's NOT planned.
R6 Encrypted FK references via blind indexing (replace plaintext UUID FKs with HMAC blind indexes) CANDIDATE — not committed Would remove the "this user has N transactions" pattern visible to a DB reader. Same trade-off as R5: real complexity for marginal gain since UUIDs are already meaningless.
The honest line. R5 and R6 are listed as candidates not because they're planned but because the next reader of this doc deserves to know what is and isn't being worked on. Plaintext fields earn their place by serving a specific architectural role (filtering, joins, RLS, crypto versioning, structural integrity). When a new field is added to V3, the default is encrypted — plaintext requires explicit justification on this same table.

The end-to-end flow when V3 receives canonical data

1

User unlocks V3 vault

Browser derives the Master Encryption Key (MEK) from the user's vault password using Argon2id. The MEK exists only in browser memory.

2

V3 calls or-sync

V3 edge function adds OR_PLATFORM_API_KEY + the user's subaccount_id + the session-only encryption key. OR runs the source adapter (e.g. Blink) and returns canonical transactions.

3

V3 requests its sink format

V3 calls or-transactions-list?format=bitbooks-v3. OR's V3 sink adapter applies the App Profile YAML, runs the account-mapping rules, and returns rows shaped exactly for V3's three tables — with requires_encryption metadata listing which fields the browser must encrypt.

4

V3 browser encrypts the sensitive fields

For each row, browser AES-256-GCM-encrypts the listed fields using the MEK-derived data key. OR never sees the encrypted output.

5

V3 inserts into its tables

Standard Supabase insert. Cala receives matching blind entries (UUIDs + dummy 1 USD amounts) for the journal entries. Real values stay in V3's encrypted columns, decryptable only in the user's browser.

What V3 never had to write. Strike parser. Cash App parser. BTCPay parser. Lunar Rails parser. Flash parser. CCXT integration. CSV importer. Account-mapping rules per provider. All of that lives in OR. V3's only contribution was the App Profile YAML — written once, applied forever.

Anatomy of a domain module

Every module follows the same three-part template. Once a domain is decided, the work is filling in this template — not redesigning the protocol.

module: insurance
version: v1
requires_canonical: v1     # the core canonical version this module is compatible with

# 1. New transaction-type values added to the type enum
new_transaction_types:
  - premium_payment
  - claim_disbursement
  - policy_issuance
  - policy_renewal
  - policy_cancellation

# 2. Optional extensions added to existing core entities
extensions:
  - on: CanonicalTransaction
    field: insurance
    when: type in [premium_payment, claim_disbursement, policy_issuance, policy_renewal, policy_cancellation]
    schema:
      policy_id: string             # reference to a CanonicalPolicy entity
      coverage_period: { start: date, end: date }
      claim_id: string?             # optional, for claim_disbursement

  - on: CanonicalAccount
    field: insurance
    when: type == 'insurance_account'
    schema:
      carrier: string
      policy_count: number

# 3. New top-level entities the module introduces
new_entities:
  - name: CanonicalPolicy
    schema:
      id: string
      canonical_version: 'v1'
      module: 'insurance/v1'
      policy_type: 'auto' | 'home' | 'health' | 'life' | 'business' | 'crypto'

      beneficiary: string?
      deductible: { value: string, currency: string }

That's it. The module is fully described by the template. OR's protocol library validates it, registers it, and from then on any source adapter can emit insurance entities and any sink consumer can declare it accepts them.

Cross-module relationships

Real life is messy: a single real-world event often touches multiple modules. The protocol handles this via two patterns already in the core:

  1. Multi-module markers on a single canonical record. A premium payment IS an insurance event AND a banking transaction. The record carries modules: [insurance, banking]. Consumers that accept either module ingest it; OR's routing handles the union.
  2. related_transaction_ids on Transaction (already exists). A claim disbursement (insurance module) links to the underlying bank deposit (banking module) via related_transaction_ids: ["banking_tx_xyz"]. Sinks that import both see them connected; sinks that import only one see only their side.

Versioning + the staircase of module evolution

Each module has its own version. The core canonical version moves slowly (years). Modules can iterate faster (months) as their domains mature. Source adapters declare which module versions they emit; sink consumers declare which they accept; OR holds at least the last 2 versions of each module live for graceful migration.

canonical_core: v1          # slow-moving, stable

Bottom line

Yes — this scales, and it scales the way every successful financial-data platform has scaled. The protocol is modular by design. Insurance, derivatives, investments, lending, payroll, real estate, and whatever the next domain demands all drop in as opt-in modules following the same three-part template (new types + extensions on existing entities + new top-level entities). Source adapters declare what they emit; sink consumers declare what they accept; OR routes the intersection. The canonical core stays small and stable. Module versioning lets each domain evolve independently. The pattern is proven at FDX (130M+ accounts), Plaid, Stripe, and Quiltt — they all started narrow and grew exactly this way.
Same privacy guarantees apply to every module. Insurance data, derivative positions, payroll earnings — all flow through the same encrypted-credentials, pull-through, browser-encrypts-on-insert architecture as Bitcoin transactions do today. New domains don't earn relaxed privacy by virtue of being new. The ZKA contract is part of the core, not a per-module decision.

Quiltt's API normalizes many underlying providers behind a single developer interface. OR writes one Quiltt source adapter; every BitBooks consumer (V2 today, V3 future, OW) gains the entire downstream institution list with zero per-consumer code.

💳

BitBooks-pays billing model

BitBooks pays Quiltt for the customer's usage rather than each customer holding their own Quiltt account. The customer experience is "click connect" — no separate signup, no separate bill. Cost shows up in BitBooks' COGS, not on the customer's invoice.

🪆

Same protocol = same deployment

Whether the source is Blink (one provider), CCXT (100 exchanges), Quiltt (many institutions), or SimpleFIN (12,000 banks), the canonical output is identical. Consumer apps don't know — and don't need to know — how many institutions sit behind a given source. Same insert path always.

⚖️

The trade-off, named

Wrapping a closed aggregator (Quiltt, Plaid) creates a dependency that could shut off (Zabo precedent). Mitigation: keep multiple aggregator options live (Quiltt + Plaid + SimpleFIN), document switch-over playbook, and treat the open-source CCXT/SimpleFIN paths as fallbacks. The open canonical spec means a switch never requires a consumer-app change.

Pull-through flow with Quiltt (matches OR's default mode)

1

One-time merchant setup

Merchant clicks "Connect bank" inside V3 → OR Connect Widget loads → Widget embeds Quiltt's hosted Connector UI → Merchant picks bank, authenticates via Plaid/MX/Akoya/Finicity (whichever Quiltt routed to) → Quiltt issues a session token. 2

Quiltt fires webhook (wake-up only)

When new transactions arrive at Plaid/MX/etc., Quiltt's API surfaces them and fires a webhook to OR with the event ID. OR receives it and sends a Web Push wake-up to V3's service worker. OR stores no payload.

3

V3 pulls fresh data

V3 wakes, vault unlocks (or already is), V3 calls or-sync with session key. OR decrypts the Quiltt session token in memory, calls Quiltt's GraphQL { transactions(filter: {since: $cursor}) { ... } }, requests only the canonical fields it needs (Quiltt's GraphQL = selective fetch). Result translated to canonical, sink adapter applied, V3-shaped rows returned in response.

4

V3 encrypts + inserts

V3 browser encrypts the listed fields with the MEK, inserts into V3's tables, sends matching blind entries to V3's Cala via the cala-proxy. OR's RAM is wiped after the response. OR's stored cursor advances. Done.

Why Quiltt makes OR's life easier (technical details)

  • GraphQL = selective fetch. OR requests only the canonical fields it needs. Less data on the wire, less surface area, easier to audit.
  • Hybrid REST+GraphQL. OR uses GraphQL for queries, REST for connection lifecycle (create, revoke, status checks). Fits OR's existing patterns.
  • Session token auth + revocation. Token-based auth fits the encrypt-creds-in-browser model. Quiltt supports revocation, so when a user disconnects in V3, OR cascades the revoke to Quiltt cleanly.
  • Custom Metadata field. OR carries its subaccount_id through Quiltt as Custom Metadata, so the multi-tenant routing is recoverable from any Quiltt API response without OR keeping a separate translation table.
  • Aggregator failover under the hood. If Plaid is down for Bank X, Quiltt automatically routes through MX or Akoya. OR's code doesn't know — and doesn't need to know — which aggregator is active. This is the canonical-pattern benefit, applied at the floor below us.
  • Rate limit headroom. 100 req/sec authenticated. OR's per-merchant sync is well below that ceiling even at scale.
  • API versioning convention. Quiltt uses dated API versions (current: 2026-04-01). Matches OR's canonical_version philosophy — both sides version their contracts explicitly.

CSV upload is just another source adapter — authType: 'csv-upload', no credentials, takes a file plus a template hint. The protocol turns "every app needs its own Strike CSV importer" into "Strike CSV is one template in OR, available everywhere."

  required_columns: [Date, Type, Amount, Currency]

  Date: { to: occurred_at, parse: 'iso8601' }

26 The SimpleFIN Pattern — Open Spec + Reference Implementation

SimpleFIN's architecture is the strongest defense against the Zabo precedent (closed aggregator gets acquired by Coinbase and shuts off your dependency in 14 days). The pattern: publish the spec, run the reference implementation, let anyone build alternatives.

What SimpleFIN gets right

  1. Spec is public and CC-licensed. Anyone can implement either side without asking permission.
  2. Hosted bridge service is just one implementation. $1.50/month for convenience, but anyone can run their own bridge.
  3. Format is dead simple. JSON. No SDK required. curl works.
  4. Read-only. No write capability means lower attack surface and easier user trust.
  5. Versioned. v1 → v2 transitions handled gracefully via content negotiation.

OR's spec publication plan

1

Publish at orangerails.org/spec/v1

JSON Schema for each canonical entity + TypeScript type definitions + Markdown reference docs. License: CC-BY-SA 4.0.

2

Versioned content negotiation

Request includes Accept: application/orangerails+json; version=v1. Server returns matching version or 406 with available versions list.

3

Reference implementation = hosted OR

The OR-hosted service runs the spec. Self-hosted OR runs the same spec via Docker Compose. Third-party implementations welcome.

4

Compliance test suite

Open-source conformance tests so any implementation can self-certify spec compliance.

The protocol moat. Apache 2.0 alone isn't a moat — anyone can fork. The moat is the network of implementations that converge on the spec. Once V2, V3, OW, rotki, and third-party apps all speak the protocol, the protocol wins. The hosted service is just the most convenient implementation.

29 Key Decisions

#DecisionRecommendationReason
D1 Where does account mapping live? App Profile in OR, with per-subaccount override Makes OR true "Plaid for Bitcoin" — click and done. Apps stay thin.
D2 How is the canonical model versioned? Every record carries canonical_version. Apps declare canonical_version_supported. OR keeps last 2 versions live. Lets v2 ship without breaking v1 consumers. Standard pattern (k8s, GraphQL, FDX).
D3 Can OR write directly to apps' DBs? No. OR returns shaped rows; app does the insert. Keeps OR stateless on the sink side. Apps own their schema migrations. ZK apps need browser encryption pass before insert.
D4 Where does CSV upload happen? OR Connect Widget, embedded in app Consistent UX. OR owns the template library. App gains all CSV formats free.
D5 Where do App Profiles live? OR's app_profiles table, edited from Developer tab Single source of truth. Versioned. Visible to all OR maintainers.
D6 Push, Pull, or both? Both, gated by tier. Pull on Sandbox/Production, Push (webhooks) on Enterprise. Matches the pricing page. Pull works everywhere. Webhooks need ops.
D7 What about V3's existing Blink parsing code? Migrate to OR sink adapter, delete from V3 This is the work the realization unblocks. Keeping V3-side parsing locks in the duplication you want to escape.
D8 Bidirectional providers (V3-as-source)? Yes, with explicit user consent per downstream Unlocks cross-product mirroring, third-party integrations, exports. Consent-first prevents silent data flow.
D9 Use CCXT for exchanges? Yes — wrap it directly 100+ exchanges Day 1. MIT-compatible. Saves 6–12 months. Community maintains upstream API changes.
D10 Publish canonical spec publicly? Yes — CC-BY-SA at orangerails.org/spec/v1 The Zabo defense. Lets rotki, Maybe, anyone implement. Turns OR from a service into a protocol.

30 Glossary

N × M Problem
The integration explosion that happens without a canonical format: N data sources × M consumer apps = N×M custom integrations. With a canonical format: N + M.
Canonical Model
The shared format every source translates INTO and every consumer translates FROM. The contract that makes the protocol work.
Source Adapter
A module that knows how to talk to one provider (Blink, Flash, Strike) and emit canonical entities. Lives in OR.
Sink Adapter
A module that knows how to take a canonical entity and produce rows shaped for one consumer app (V3, V2, OrangeWay). Lives in OR.
App Profile
A YAML config a consumer app publishes to OR that tells OR how to shape data for that app — table names, field mappings, account-mapping rules, encryption requirements.
Platform
A consumer of the OR API. Holds a long-lived API key. Each BitBooks family product is a separate platform.
Subaccount
An end user as OR sees them. Belongs to one platform. Identified by an opaque UUID — no PII, no email, no auth credentials.
Zero-Knowledge (ZK)
Architecture where the server cannot read user data without an active user session. Credentials encrypted in browser before reaching the server. Server stores ciphertext only.
MEK (Master Encryption Key)
Derived in the user's browser from their vault password using Argon2id. Never stored, never transmitted. Lives only in browser memory during an active session.
Cala
Galoy's open-source double-entry accounting ledger (Rust, Apache 2.0). Used as the ledger backend by V3 (V2 has its own non-Cala Postgres ledger). The Cala Mapping Pattern (Section 13) lets any future Cala-using app inherit OR's account-mapping rules.
FMV (Fair Market Value)
The BTC/fiat exchange rate at the exact moment of a transaction. Required for GAAP/IFRS compliance. Stored as fiat_equivalent in canonical Transaction.
CCXT
MIT-licensed library that wraps 100+ crypto exchanges with one normalized API. OR uses CCXT as the basis for its exchange source adapter.
FDX (Financial Data Exchange)
US Open Banking industry standard. 130M+ accounts, 250+ orgs, 2.2B API calls/month as of early 2026. OR borrows naming conventions from FDX where neutral.
SimpleFIN
Open protocol for read-only financial data (v2.0.0 March 2026). The architectural pattern OR borrows: publish the spec, run a reference implementation, let anyone build alternatives.
NWC (Nostr Wallet Connect)
Bitcoin Lightning protocol that lets apps interact with any NWC-compatible wallet. One OR adapter unlocks the entire NWC wallet ecosystem (Coinos, Alby, Flash Wallet, Mutiny).
